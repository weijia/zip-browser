# ZB 清单与目录大小需求

更新时间：2026-11-16

适用代码：`C:\codes\nodejs\zip-browser\web`（zb 前端原始代码）

## 1. 背景

当前 zb 的清单生成面板已经具备：

- 目录结构清单（`struct` v2）；
- 文件列表清单（`file-list`）；
- 生成预览、下载 ZIP、上传到 zen-fs-config 同步组；
- 目录体积统计接口 `/zb/api/mft/scan`；
- 文件大小已经由 `/zb/api/list` 返回，并存入选区。

但实际使用中存在两个问题：

1. 点开目录时，目录树要等目录大小算完才完整显示，展开不够快。
2. 目录大小查询是逐个目录发请求，选多个目录时请求次数多；同时 OpenList 的扫描请求是“整个请求共享一个 deadline”，一次塞太多根目录会让后面的目录变成 `partial`。

目标是把“看子目录”和“算目录大小”拆成两条独立链路：

- **看子目录要快**：点开目录后立刻看到下一层，不等待体积扫描。
- **目录大小可以慢**：后台异步计算、批量查询、缓存复用，算完再更新徽标。

## 2. 目标

### P0 必须满足

1. **展开目录不阻塞**
   - 点击目录展开时，只请求当前目录的下一层子目录。
   - 子目录列表返回后立即渲染，不等 `/api/mft/scan`。
   - 目录大小只作为异步补充信息，晚到不影响展开。

2. **目录大小异步计算**
   - 用户勾选目录、或展开需要显示大小的目录时，先显示“计算中…”。
   - 扫描完成后更新为：`N 个文件 · 逻辑大小 X · 占用 Y`。
   - 失败或超时显示“计算失败/部分不可读”，允许重试。

3. **多个目录批量查询**
   - 不能一个目录一个请求地串行查。
   - 多个未缓存目录合并成一批，使用一次 `/zb/api/mft/scan` 请求。
   - 批次大小、超时时间可配置；默认建议 4 个根一批。

4. **路径级缓存**
   - 后端返回的 `summaries` 包含根目录及其所有子孙目录，全部写入前端缓存。
   - 再次选中同一目录或其子目录时，命中缓存则零请求。
   - 只有手动刷新或清空缓存才重新计算。

5. **扫描根去重**
   - 同时选中父目录和子目录时，只保留父目录作为扫描根。
   - 避免同一棵子树被重复扫描。

6. **文件大小不触发扫描**
   - 文件列表里单个文件的 `size` 直接来自 `/zb/api/list`，立即显示。
   - 不因为显示文件大小而请求 `/api/mft/scan`。

7. **上传使用最新选择集**
   - 选择集变化后，旧的 `lastScan` 必须失效。
   - “上传到同步组”不能再因为 `lastScan` 非空就上传旧清单。
   - 上传的 JSON 必须与当前选择集、当前预览一致。

### P1 应该满足

1. 目录行、文件行都能看到大小。
2. 顶部显示当前选择汇总：
   - 已选目录数、文件数；
   - 源文件逻辑大小合计；
   - 预计清单 JSON 大小。
3. 每个目录行可以单独“重新计算大小”。
4. 移动端目录行不横向溢出，大小徽标可换行或截断。

### 非目标

1. 不在本需求中实现“上传真实文件内容”。当前 zb 只上传清单 JSON，不上传文件本体。
2. 不引入服务端目录大小索引；目录大小仍然靠扫描得到。
3. 不改变 zen-fs-config 同步组协议。

## 3. 关键语义：清单层数与体积口径必须分开

当前实现把“清单展开几层”和“体积扫描多深”耦合在一起：

- `recursive=false` 表示清单只写一层；
- 但目录结构清单的扫描根固定带 `sizeFull: true`；
- 后端 `entryRecursive || entrySizeFull` 会让 `sizeFull` 强制递归整棵树；
- 扫描后再用 `stripScanFiles(node, false)` 把返回结构裁成一层。

结果：

> “仅本层”只代表清单结构只写一层，不代表只扫一层；为了准确体积，仍然扫整棵树。

这对“快速看子目录”不利。需求上必须拆成两个独立维度：

| 维度 | 选项 | 说明 |
|---|---|---|
| 清单层数 | 仅本层 / 含所有子目录 | 决定写入 manifest 的结构深度 |
| 体积口径 | 快速（只算当前层） / 精确（整棵子树） | 决定是否递归扫描 |

推荐前端提供两个独立控件，而不是只靠一个 `recursive`：

- **仅本层 + 快速**：`recursive=false, sizeFull=false`，只列一层，不递归算子树大小。
- **仅本层 + 精确**：`recursive=false, sizeFull=true`，结构只写一层，但接受后端整棵扫描。
- **全部 + 精确**：`recursive=true, sizeFull=true`，结构、大小都是整棵。
- **全部 + 快速**：`recursive=true, sizeFull=false`，结构整棵，但不要额外的全量体积语义。

注意：`sizeFull` 目前在 OpenList 后端只是一个“强制递归”的开关，不是独立的“体积开关”。如果后续要严格支持“只算一层”，需要后端增加真正的 `includeSize` / `sizeScope` 语义，或者前端明确接受“精确体积必须整棵扫描”。

## 4. 目录展开链路

### 当前行为

- `manifest-builder.js:368-386` 的 `expandNode()` 调 `/api/mft/tree?path=...`，只取下一层目录，已经是快速路径。
- `/api/mft/tree` 只返回目录节点，不返回体积。
- 目录结构清单的 `renderDirs()` 在 `manifest-builder.js:75-106` 读取 `dirSummaryCache` 或 `lastScan.summaries` 显示体积。

### 需求行为

1. 点击目录：
   - 立即把节点标记为“加载中”；
   - 请求 `/api/mft/tree?path=...`；
   - 返回后马上渲染下一层子目录；
   - 不等待任何体积接口。

2. 体积补全：
   - 如果该目录已有缓存，直接显示；
   - 如果没有缓存且该目录已被选中，加入后台批量队列；
   - 未选中的目录默认不自动计算，避免用户随便展开就触发大量扫描；
   - 用户可对单目录点“计算大小/刷新”主动触发。

3. 展开过程中不出现“整页 loading”或阻塞式弹窗；只在该行显示局部状态。

### 4.1 展开数据缓存

展开得到的“下一层子目录”也必须缓存，而且必须是**路径级缓存**，不能只依赖当前 DOM 节点上的 `dataset.loaded`。

当前 `expandNode()` 在 `manifest-builder.js:375-378` 用 `childrenEl.dataset.loaded === '1'` 做缓存，问题是：

- 这个标记只存在于当前 DOM 节点；
- `renderDirs()` 每次重建树节点后，标记就丢失；
- 切换标签、重新渲染、选择集变化后，再展开同一目录仍会重新请求 `/api/mft/tree`；
- `expandNode()` 失败时在 `manifest-builder.js:387-390` 也把 `dataset.loaded` 设为 `1`，导致失败目录无法再次重试。

需求：

1. 新增 `treeCache` 或 `dirTreeCache`，键为完整目录路径，值为：
   ```js
   { children, updatedAt, error? }
   ```
2. 展开目录时先查缓存：
   - 命中且未过期：直接渲染，不发请求；
   - 命中但已过期：可先显示旧数据，再后台刷新（stale-while-revalidate）；
   - 未命中：显示“读取中”，请求 `/api/mft/tree`。
3. 同一路径并发展开只允许一个在途请求（in-flight dedup），后到的调用复用同一个 Promise。
4. 请求成功写缓存；请求失败**不写永久缓存**，UI 显示“读取失败，点击重试”，不能被 `loaded=1` 卡死。
5. 缓存 TTL 建议与 dir-struct-gen 的目录缓存对齐，默认 5 分钟；用户手动“刷新子目录”或“重新扫描并生成”时清除对应路径缓存。
6. 展开缓存与目录大小缓存分开：
   - `treeCache` 只存下一层目录结构；
   - `dirSummaryCache` 只存体积；
   - 展开目录不因为体积未算完而失效，体积算完也不重新请求目录结构。
7. 对 `zip:` 等临时会话路径，缓存必须随会话关闭而清除，不能跨会话复用。

## 5. 批量查询设计

### 5.1 最小扫描根

新增或调整根收集逻辑，输入：

- 目录结构清单的选中目录；
- 文件列表清单里的目录；
- 当前需要计算大小的目录。

处理：

1. 归一化路径，按路径长度排序；
2. 如果某个路径的祖先已经在根集合中，跳过该路径；
3. 每个根带上：
   ```json
   { "path": "...", "recursive": true, "sizeFull": true }
   ```

### 5.2 分批请求

建议参数：

- `SCAN_BATCH_SIZE = 4`；
- `SCAN_BATCH_TIMEOUT_MS = 60000` 或 `90000`；
- 每批独立请求、独立超时、独立失败。

请求体：

```json
{
  "paths": [
    { "path": "C:\\A", "recursive": true, "sizeFull": true },
    { "path": "C:\\B", "recursive": true, "sizeFull": true }
  ],
  "recursive": true,
  "timeoutMs": 60000
}
```

### 5.3 结果合并

每批返回后：

- 合并 `roots`；
- 合并 `summaries`；
- 合并 `files`；
- 合并 `status`；
- 把 `summaries` 里的每个路径写入 `dirSummaryCache`；
- 更新对应行的体积徽标；
- 记录本批是否失败，不影响其他批。

### 5.4 缓存策略

- 缓存键：目录绝对路径；
- 缓存值：`fileCount / totalSize / totalSizeOnDisk / partial / updatedAt`；
- 命中缓存不发请求；
- 默认不自动过期，只在用户点“刷新”或“重新生成”时更新；
- 目录列表本身可以单独做短 TTL 缓存，避免重复 `/api/mft/tree`。

### 5.5 超时与 partial

OpenList 的 `/zb/api/mft/scan` 限制：

- 单请求最多 100 个路径；
- 默认 20 秒，最大 120 秒；
- `deadline` 是整个请求共享的；
- 根目录之间顺序处理；
- 单个根内部递归子目录并发上限 6；
- 最大深度 24；
- 每目录最多 20000 个文件。

因此：

- 不能把几十个大目录塞进一个请求，否则前面的根用完 deadline，后面的根会 `sizePartial=true`；
- 一批 4 个，并给每批 60～90 秒，能显著降低“后面的目录全是 partial”的概率；
- `partial` 必须显示为“部分不可读/数值为下界”，不能当作准确值。

## 6. 文件大小链路

- `/zb/api/list` 返回文件项时已经带 `size`、`mtime`；
- `addPickedFromItem()` 在 `manifest-builder.js:614-625` 已经把 `size/sizeOnDisk/mtime` 存进文件选择集；
- `file-list-export.js:165-173` 和 `287-295` 会把 `size/sizeOnDisk/mtime` 写进文件列表 JSON；
- 因此文件行只需要在 `renderFiles()`（`manifest-builder.js:123-154`）里显示 `formatBytes(item.size)`，不需要任何扫描请求。

对于“文件列表里同时有目录”的情况：

- 目录行显示整棵子树汇总，走批量 summary；
- 文件行显示单文件大小，直接用已有数据；
- 两类行不要共用同一个“计算中”队列，避免文件被目录扫描拖慢。

## 7. 上传链路

现有上传：

- 按钮：`index.html:154` “上传到同步组”；
- 处理：`manifest-builder.js:683` 绑定 `builderUpload`；
- 实现：`manifest-builder.js:482-497` 的 `upload()` 调 `syncScanNow()`；
- 单目录上传：`manifest-builder.js:577-582` 的 `fl-scan-one`，先 `doScan([path])` 再 `upload()`。

需求：

1. 选择集变化后立即把 `lastScan` 标记为过期；
2. 上传前如果过期，必须重新扫描，不能复用旧结果；
3. 上传前显示预检摘要：
   - 目标同步组；
   - 选中目录/文件数量；
   - 源文件大小；
   - 清单 JSON 预计大小；
4. 上传仍只写清单 JSON，不写文件内容；
5. 上传失败只提示失败，不破坏已有本地选择集。

## 8. UI 状态

目录行建议状态：

- `未计算`；
- `计算中…`；
- `N 个文件 · 逻辑大小 X · 占用 Y`；
- `N 个文件 · 逻辑大小 X · 占用 Y · 部分不可读`；
- `计算失败，点此重试`。

交互要求：

- 计算中不阻塞展开、不阻塞勾选、不阻塞其他目录操作；
- 同一路径重复点击不重复发请求；
- 取消勾选不清除已算缓存；
- 移动端大小徽标不能把路径挤到不可见。

## 9. 验收标准

1. 点击目录展开，子目录列表在体积扫描完成前就能显示。
2. 选中 10 个目录并计算大小，请求数不超过 `ceil(10/4)=3` 次（去重后更少）。
3. 父目录与子目录同时选中时，只扫描父目录，不重复扫描子目录。
4. 扫描父目录后，子目录大小命中缓存，再选子目录不产生新请求。
5. 某批扫描失败/超时，其他批结果仍然保留，失败批可重试。
6. 任意目录显示 `partial` 时，UI 明确标为“部分不可读/下界”。
7. 文件行显示大小不需要 `/api/mft/scan` 请求。
8. 选择集变化后点“上传到同步组”，上传的是最新清单，不是旧 `lastScan`。
9. 上传内容仍然只有清单 JSON，不包含真实文件内容。
10. 展开过的目录在重新渲染、切换标签、再次展开时命中 `treeCache`，不重复请求 `/api/mft/tree`。
11. 同一路径并发点击展开只产生一个请求；请求失败后可以再次点击重试，不会因为 `dataset.loaded=1` 永久卡死。
12. `treeCache` 与 `dirSummaryCache` 互不影响：体积未算完不妨碍展开，展开命中缓存也不跳过体积计算。

## 10. 当前代码现状与差距

| 项目 | 现状 | 差距 |
|---|---|---|
| 展开子目录 | `expandNode()` 调 `/api/mft/tree`，只取一层 | 基本满足快速展开；需确认不被体积逻辑阻塞 |
| 展开数据缓存 | 只依赖当前 DOM 的 `dataset.loaded`；重新渲染后丢失；失败也标记 loaded | 需要路径级 `treeCache`、TTL、在途去重、失败可重试 |
| 单目录体积 | `loadDirSummary()` 一次一个路径，`timeoutMs: 20000` | 需要改成批量队列 |
| 清单扫描 | `doScan()` 已把所有 roots 放进一个请求 | 没有分批、没有 `timeoutMs`、没有祖先去重 |
| 后端多路径 | `/zb/api/mft/scan` 支持 `paths` 数组，最多 100 | 单请求共享 deadline，不能无限塞 |
| 体积缓存 | `dirSummaryCache` 存在，但 `doScan` 只依赖 `lastScan.summaries` | 应把每批 `summaries` 全部写入缓存 |
| 文件大小 | 已采集、已写入文件列表 JSON | `renderFiles()` 未显示 |
| 上传 | `upload()` 复用 `lastScan` | 选择集变更后可能上传旧扫描 |
| 层数与体积 | `sizeFull` 强制递归 | 需要拆成独立“体积口径”选项 |

## 11. 实施阶段建议

### 阶段 1：拆开“展开”和“算大小”

- 保持 `expandNode()` 只走 `/api/mft/tree`；
- 新增路径级 `treeCache`（默认 TTL 5 分钟、在途去重、失败可重试）；
- 新增目录大小异步队列，不阻塞展开；
- 只在选中目录或用户主动请求时计算大小。

### 阶段 2：批量扫描

- 实现最小根去重；
- 实现 `fetchScanBatches()`，默认 4 个一批、每批 60～90 秒；
- 合并 `roots/summaries/files/status`；
- 把全部 `summaries` 写入 `dirSummaryCache`。

### 阶段 3：UI 大小显示

- 目录行显示计算中/结果/partial/重试；
- 文件行显示 `size`；
- 顶部显示选择汇总。

### 阶段 4：上传一致性

- 选择集变化使 `lastScan` 失效；
- 上传前预检并重新扫描（如需要）；
- 保持“预览 = 上传”的同一份载荷。

## 12. 待确认

1. “仅本层 + 精确大小”是否接受后端仍然整棵扫描？如果不接受，需要后端新增真正的“只算当前层”语义。
2. 未选中的目录展开时，是否也要自动算大小？建议默认不算，避免浏览即触发大量扫描。
3. 目录大小缓存是否需要过期策略？建议默认不过期，只手动刷新。
4. 文件列表里的目录是否也需要整棵子树大小？如果不需要，可只显示文件大小，进一步减少扫描。
5. 上传预检是否需要显示“清单 JSON 大小”和“源文件大小”两个数字？建议显示，避免误解为上传文件内容。
